Simulated PSP — High-Level Design
1. Purpose

The project uses a Simulated Payment Service Provider (PSP) to model the behavior of an external payment provider without integrating a real PSP initially.

The PSP is intentionally implemented as a separate service with its own database. The goal is not to reproduce the complete internal architecture of providers such as Stripe, Razorpay, or Juspay. Instead, it provides the minimum provider-side behavior required to study payment reliability, recovery, and later RabbitMQ-based asynchronous processing.

The gateway communicates with the PSP through an API/provider abstraction rather than accessing the PSP database directly.

Payment Gateway
      |
      | HTTP / Provider Interface
      v
Simulated PSP
      |
      v
PSP Database
2. Why a Separate PSP Service?

The PSP represents an external system boundary.

The gateway owns its own payment state, while the PSP owns its own provider-side payment state.

Gateway
-------------------------
payment_id
status
provider_payment_id
...

        |
        | external communication
        v

Simulated PSP
-------------------------
provider_payment_id
gateway_payment_id
status
...

Keeping the PSP separate allows the project to simulate situations where the two systems temporarily disagree.

For example:

Gateway: PROCESSING
PSP:     SUCCESS

This is an important distributed-systems scenario because the gateway and PSP do not share one database transaction.

3. PSP Database

The simulated PSP has its own PostgreSQL database and a provider_payments table.

The table represents the PSP's record of the provider-side payment.

High-level structure:

ProviderPayment
----------------------------
provider_payment_id
gateway_payment_id
amount
currency
status
failure_reason
created_at
updated_at
Important identifiers

gateway_payment_id

The payment identifier generated by the gateway. It is persisted by the PSP so that a provider-side payment can be correlated back to the gateway payment.

provider_payment_id

The identifier generated by the PSP for its own payment record.

The relationship is therefore:

Gateway Payment
pay_123
     |
     v
PSP Payment
psp_456

gateway_payment_id is unique in the simulated PSP so that the same gateway payment does not result in multiple provider-payment records.

4. PSP Payment States

The simulator currently supports three payment states:

PROCESSING
SUCCESS
FAILED
PROCESSING

The PSP has a payment record, but the final payment outcome is not yet known.

SUCCESS

The PSP has determined that the payment succeeded.

FAILED

The PSP has determined that the payment failed.

These states represent the provider-side payment lifecycle. Communication problems such as timeout are not treated as payment states.

5. Simulated PSP API

The PSP exposes a small API sufficient for the gateway reliability experiments.

Conceptually:

POST /payments

Creates or identifies a provider-side payment.

GET /payments/{provider_payment_id}

Retrieves a payment using the PSP's own identifier.

GET /payments/by-gateway/{gateway_payment_id}

Finds the provider payment associated with a gateway payment.

The last operation is particularly useful when the gateway does not yet know the provider_payment_id, for example after an uncertain communication failure.

6. Simulated Payment Outcomes

The PSP simulator can deliberately produce several controlled scenarios.

SUCCESS
Gateway → PSP
             ↓
        create payment
             ↓
          SUCCESS
             ↓
        normal response

The PSP persists the payment as SUCCESS and returns the result.

FAILED
Gateway → PSP
             ↓
        create payment
             ↓
           FAILED
             ↓
        normal response

The PSP persists the payment as FAILED and provides a failure reason.

PROCESSING
Gateway → PSP
             ↓
        create payment
             ↓
         PROCESSING
             ↓
        normal response

The PSP persists the payment as PROCESSING.

The gateway therefore cannot treat the payment as completed yet.

7. Timeout Simulation

Timeouts are used to demonstrate that communication failure does not imply payment failure.

Two useful timeout scenarios are simulated.

Timeout Before Creation

The PSP delays before creating the provider payment.

Gateway
   |
   | payment request
   v
PSP
   |
   | waits
   X
Gateway timeout

The PSP has not created a payment.

Timeout After Creation

The PSP creates and commits the provider payment first, and only then delays its response.

Gateway
   |
   v
PSP
   |
   ├── create payment
   ├── commit
   |
   └── delay response
            X
        Gateway timeout

The important result is:

Gateway:
PROCESSING / uncertain

PSP:
payment exists

This demonstrates why the gateway must not convert a timeout directly into FAILED.

The eventual recovery mechanism can query the PSP to determine what happened.

8. PSP Internal Error

The simulator can also deliberately generate an internal PSP failure.

Conceptually:

Gateway
   |
   v
PSP
   |
   └── internal failure
          ↓
      HTTP 500

An HTTP 500 means the PSP failed to complete the request successfully.

However, the gateway should not automatically interpret:

HTTP 500

as:

Payment = FAILED

because the gateway cannot necessarily know whether the provider-side payment was created before the internal failure.

Therefore provider-side errors such as internal failures belong to the uncertain-outcome/recovery category unless the PSP explicitly returns a definitive payment result.

9. Response Loss

Response loss is intentionally not modeled as a PSP application error in the current PSP service.

This distinction is important.

A response being lost means:

PSP successfully processes the payment
        ↓
response does not successfully reach the gateway

It is a communication-layer problem, not a PSP payment-state problem.

Therefore the current simulator does not treat response loss as:

HTTP 500

or another PSP business error.

When the gateway integration is implemented, response loss can be simulated at the provider communication/client layer so that:

PSP database:
payment exists

Gateway:
no usable response received

This gives us the exact uncertainty needed for recovery testing without incorrectly representing response loss as an internal PSP failure.

10. Core Reliability Principle

The simulated PSP exists primarily to test this rule:

A failed communication attempt does not prove that the payment failed.

Therefore:

SUCCESS response
    → SUCCESS

FAILED response
    → FAILED

PROCESSING response
    → PROCESSING

Timeout
    → remain PROCESSING / uncertain

Connection failure
    → remain PROCESSING / uncertain

PSP internal error
    → remain PROCESSING / uncertain

The uncertain cases must eventually be resolved through provider-side state retrieval rather than blindly creating another payment.

11. Provider Status Recovery

The PSP maintains enough persistent information for the gateway to recover an uncertain payment.

For example:

Gateway
payment_id = pay_123
provider_payment_id = NULL
status = PROCESSING

PSP:

gateway_payment_id = pay_123
provider_payment_id = psp_456
status = SUCCESS

The gateway can ask:

Find PSP payment for pay_123

The PSP returns:

provider_payment_id = psp_456
status = SUCCESS

The gateway can then reconcile its own state:

PROCESSING → SUCCESS

No second payment needs to be created.

12. Scope of the Simulator

The simulated PSP is intentionally limited.

It does not attempt to model the complete internals of a production PSP, such as:

authorization systems
capture systems
refund systems
settlement
acquirer networks
banking rails
disputes
chargebacks
multiple payment attempts

Those concerns are outside the current project scope.

The simulator exists to provide a controlled external system with:

persistent provider-side state
provider-side identity
payment status
status lookup
controlled success/failure
controlled communication failures

This is enough to study the gateway's behavior before introducing RabbitMQ.

13. Role in the Overall Project

The current architecture is therefore:

                    Payment Gateway
                          |
                          v
                   PaymentService
                          |
                          v
                PaymentServiceProvider
                          |
                          v
                   Simulated PSP
                          |
                          v
                     PSP Database

Later, RabbitMQ will sit in front of the gateway's asynchronous processing:

Merchant
   |
   v
Gateway
   |
   v
RabbitMQ
   |
   v
Payment Worker
   |
   v
process_payment()
   |
   v
Simulated PSP

The purpose of building the PSP first is to make process_payment() capable of determining what happened to an external payment before it is exposed to RabbitMQ's at-least-once delivery and redelivery behavior.

That keeps the reliability concerns separated and allows each layer to be tested independently.
