# 2. What Problem Does Repository Solve?

Imagine we didn't have repositories.

Our AuthService might look like this:

```python
class AuthService:

    def signup(self, request):

        existing = db.execute(
            select(Merchant).where(
                Merchant.email == request.email
            )
        )

        if existing:
            raise Exception("Email already exists")

        merchant = Merchant(...)

        db.add(merchant)

        db.commit()

        return merchant
```

It works.

But notice something.

AuthService now knows:

- Business Rules
- SQLAlchemy
- Database Queries
- Transactions

It is doing **too much.**

This violates one of the most important software engineering principles:

> A component should have one primary responsibility.

---

# 3. What is a Repository?

A Repository is a component whose only responsibility is:

> Persisting and retrieving data.

Think of it as a translator.

Service speaks:

```
Create Merchant
```

Repository translates that into

```
INSERT INTO merchant ...
```

Likewise,

Service asks

```
Find merchant by email.
```

Repository translates that into

```
SELECT ...
```

The Service never worries about SQL.

---

# 4. Responsibility of Repository

Repository is responsible for:

- Creating records
- Reading records
- Updating records
- Deleting records

These four operations are commonly called

**CRUD**

```
Create

Read

Update

Delete
```

Everything else belongs elsewhere.

---

# 5. What Should NEVER Go Into Repository?

One of the easiest ways to ruin an architecture is to put business logic inside repositories.

Bad example:

```python
def signup(...):

    hash_password(...)

    create_jwt(...)

    send_email(...)
```

None of these belong here.

Why?

Because Repository should not care:

- Why a merchant is being created.
- Who requested it.
- Whether JWT exists.
- Whether email verification is enabled.

Repository only knows:

> "You gave me a Merchant.
> I know how to store it."

Nothing more.

# 7. Why Repository is a Class

Earlier we discussed

Components vs Utilities.

Repository represents a business component.

It owns

- Session
- Persistence Operations
- Entity-specific queries

Grouping everything together makes the API easier to understand.

Example:

```python
merchant_repository.create()

merchant_repository.get_by_email()

merchant_repository.get_by_id()

merchant_repository.update()
```

Instead of

```python
create_merchant()

update_merchant()

find_merchant()

delete_merchant()
```

scattered across multiple files.

---

# 8. Repository Does NOT Own Transactions

This point surprises many developers.

Suppose Signup performs

- Create Merchant
- Create Refresh Token

Should MerchantRepository call

```python
db.commit()
```

No.

Why?

Because Signup is one business operation.

If MerchantRepository commits first,

and RefreshTokenRepository later fails,

our database becomes inconsistent.

Instead,

Repositories perform persistence.

Service decides

when the entire business operation succeeds.

Then Service commits once.

```
AuthService

↓

MerchantRepository.create()

↓

RefreshTokenRepository.create()

↓

Commit
```

Notice

The transaction belongs to the business operation,

not to one repository.

---

# 9. Repository as a Database Translator

Think of Repository like Google Translate.

Service says

```
Find merchant with email.
```

Repository translates that into SQLAlchemy.

Database responds.

Repository translates database objects back into Python objects.

Service never sees SQL.

---

# 10. Repository is NOT a Service

People often confuse these.

Repository answers

> "How do I store data?"

Service answers

> "What business decision should be taken?"

Example

Repository

```python
merchant_repository.create(...)
```

Service

```python
if email already exists:

    raise EmailAlreadyExists

hash password

create merchant

store merchant
```

Repository has no idea

why the merchant is being created.

# 13. Common Mistakes

## ❌ Putting Business Logic in Repository

Wrong

```python
def login(...):

    verify_password(...)
```

Correct

```python
AuthService.login()

↓

merchant_repository.get_by_email(...)
```

---

## ❌ Returning HTTP Responses

Repository should never return

```python
JSONResponse(...)
```

or

```python
HTTPException(...)
```

Repository knows nothing about HTTP.

---

## ❌ Calling Router from Repository

Architecture should always flow downward.

```
Router

↓

Service

↓

Repository
```

Never upward.

---

# 14. Key Takeaways

✔ Repository manages persistence.

✔ Repository owns CRUD operations.

✔ Repository should not contain business logic.

✔ Repository should not know HTTP.

✔ Repository should not generate JWT.

✔ Repository should not hash passwords.

✔ Repository is a database abstraction.

✔ Service coordinates multiple repositories.

✔ Repository is reusable because it has one responsibility.

---

# Common Misconceptions

❌ Repository is just a wrapper around SQLAlchemy.

No.

It is an architectural boundary.

---

❌ Repository should commit changes.

Usually no.

The Service should decide when the business operation is complete.

---

❌ Repository replaces SQLAlchemy.

No.

Repository uses SQLAlchemy internally.

---

# Interview Questions

★★★★★ Why do we use Repository Pattern?

Because it separates persistence from business logic, making the code easier to maintain, test, and extend.

---

★★★★★ Why shouldn't Service write SQL directly?

Because it mixes business logic with persistence, violating the Single Responsibility Principle.

---

★★★★★ Why shouldn't Repository contain business logic?

Because its only responsibility is data access.

---

★★★★☆ Should Repository call commit()?

Generally no. The Service should control transaction boundaries so multiple repository operations succeed or fail together.

---

★★★★☆ Why implement Repository as a class?

Because it represents a business component that groups all persistence operations related to one entity.
