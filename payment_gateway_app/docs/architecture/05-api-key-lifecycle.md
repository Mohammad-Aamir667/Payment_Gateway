# API Key Lifecycle Implementation

## Purpose

This document explains the implementation decisions behind API key creation, retrieval, and revocation.

It focuses on the design choices made while implementing the API key management module rather than the API specifications themselves.

---

# 1. API Keys Are Stored As Hashes

The payment gateway never stores the plaintext API key.

During creation:

Merchant Request

↓

Generate Secure API Key

↓

Hash API Key (SHA-256)

↓

Store Hash

↓

Return Plain API Key Once

Only the hash is persisted inside the database.

This ensures that even if the database is compromised, attackers cannot directly obtain usable API keys.

---

# 2. Plain API Keys Are Returned Only Once

The plaintext API key exists only during the creation request.

Example:

POST /api/v1/api-keys

↓

Generate API Key

↓

Return Plain API Key

↓

Discard Plaintext

The gateway does not persist the original API key.

As a result:

GET /api/v1/api-keys

returns metadata only.

If the merchant loses the API key, it cannot be recovered.

A new API key must be generated.

---

# 3. SHA-256 Instead of bcrypt

Passwords and API keys have different security requirements.

Passwords:

- Chosen by humans
- Low entropy
- Vulnerable to brute-force attacks

Therefore passwords use bcrypt.

API Keys:

- Generated by the system
- High entropy
- Cryptographically random

The gateway stores:

SHA-256(API Key)

rather than bcrypt.

Reason:

Incoming API requests must efficiently locate the corresponding API key.

Request

↓

SHA-256(API Key)

↓

Database Lookup

↓

Merchant Authentication

Because SHA-256 is deterministic, the same API key always produces the same hash, enabling direct database lookup.

---

# 4. API Key Ownership Verification

API key identifiers are not sufficient for authorization.

After retrieving an API key using api_key_id, the implementation verifies:

APIKey.merchant_id == AuthenticatedMerchant.merchant_id

Only the owner of the API key is permitted to revoke or manage it.

This prevents merchants from operating on another merchant's credentials even if an identifier becomes known.

---

# 5. Revocation Instead Of Deletion

API keys are never physically deleted.

Instead:

key_status

↓

ACTIVE

↓

REVOKED

and

revoked_at

is recorded.

Benefits:

- Security auditing
- Credential lifecycle tracking
- Historical analysis
- Future security investigations

Once revoked, the API key can no longer authenticate requests.

---

# 6. SQLAlchemy Change Tracking

The service retrieves the API key from the repository.

After retrieval, the ORM entity becomes attached to the current SQLAlchemy session.

Updating:

api_key.key_status

and

api_key.revoked_at

is sufficient.

Calling:

db.commit()

automatically generates the corresponding UPDATE statement.

No explicit repository update() method is required.

This follows SQLAlchemy's Unit of Work pattern and keeps repositories focused on data retrieval and persistence.
