# 2. What is a Session?

One of the biggest misconceptions is:

> "Session is the database."

It is not.

Another misconception:

> "Session is the database connection."

Not exactly.

A Session is best thought of as:

> **A workspace where SQLAlchemy tracks your objects and manages a database transaction.**

Think of it like working on a Microsoft Word document.

You can:

- type
- delete
- edit
- undo

Nothing becomes permanent until you press Save.

Session behaves similarly.

You work inside the Session.

Only when you call `commit()` do the changes become permanent.

---

# 3. Session Responsibilities

A SQLAlchemy Session has four major responsibilities.

### 1. Track ORM Objects

Example:

```python
merchant = Merchant(...)
```

The Session remembers this object.

---

### 2. Generate SQL

When you perform operations,

Session converts Python objects into SQL.

---

### 3. Manage Transactions

Session decides

- begin transaction
- commit transaction
- rollback transaction

---

### 4. Identity Map

The Session remembers objects it has already loaded.

This avoids creating duplicate Python objects for the same database row.

We'll discuss this later.

# 5. db.add()

```python
db.add(merchant)
```

Many beginners think

```
INSERT executed
```

No.

`add()` simply tells SQLAlchemy

> "Please start tracking this object."

The object becomes part of the Session.

Think of adding a file to your cart before checkout.

The purchase hasn't happened yet.

---

# 6. Object States

Every ORM object has a lifecycle.

```
Transient

↓

Pending

↓

Persistent

↓

Detached
```

### Transient

```python
merchant = Merchant(...)
```

Only exists in Python.

Session doesn't know it.

---

### Pending

```python
db.add(merchant)
```

Session now tracks it.

Still not committed.

---

### Persistent

After

```python
db.commit()
```

The object now exists in the database.

---

### Detached

After Session closes,

the object still exists,

but it is no longer managed by SQLAlchemy.

# 7. db.flush()

This is one of the most misunderstood methods.

Suppose we call

```python
db.add(merchant)
```

Merchant ID is still

```
None
```

because PostgreSQL hasn't generated it yet.

Now we call

```python
db.flush()
```

SQLAlchemy immediately sends

```sql
INSERT INTO merchant ...
```

to PostgreSQL.

The database generates

```
merchant_id
```

SQLAlchemy updates the object.

Now

```python
merchant.merchant_id
```

contains the generated UUID or primary key.

Notice

The transaction is still NOT committed.

---

# 8. Why flush() Exists

This was one of your earlier questions.

Suppose Signup does

```
Create Merchant

↓

Need merchant_id

↓

Create Refresh Token
```

We cannot create

RefreshToken

until Merchant exists.

But we also don't want to commit yet.

`flush()` solves this.

```
INSERT Merchant

↓

Receive merchant_id

↓

Continue transaction

↓

Commit later
```

This is why `flush()` exists.

---

# 9. db.commit()

Commit means

> "Everything in this transaction is now permanent."

After

```python
db.commit()
```

PostgreSQL guarantees durability.

If the application crashes afterward,

the data remains.

Commit is not merely

"Save."

It is

"Finish this transaction."

---

# 10. db.refresh()

Another commonly misunderstood method.

Suppose PostgreSQL automatically fills

```
created_at

updated_at
```

using database defaults.

Python doesn't know those values.

After

```python
db.refresh(merchant)
```

SQLAlchemy performs

```sql
SELECT ...
```

and reloads the object.

Now

```python
merchant.created_at
```

contains the database-generated value.

---

# 11. Why refresh() Exists

Imagine

Database changes

```
created_at

status

version

trigger values
```

Python object becomes outdated.

Refresh synchronizes

Python

↓

Database

Again.

---

# 12. db.rollback()

Suppose Signup performs

```
Insert Merchant

↓

Insert Refresh Token

↓

Unexpected Error
```

We do NOT want

Merchant

without

Refresh Token.

Instead

```python
db.rollback()
```

undoes every SQL statement executed within the current transaction.

The database returns to its previous consistent state.

Rollback is the opposite of Commit.

---

# 13. db.close()

Many people think

```
close()

↓

Delete Session
```

Not exactly.

It means

> "Release database resources."

Connection returns to SQLAlchemy's connection pool.

Future requests reuse it.

Closing Sessions prevents resource leaks.

---

# 14. Identity Map

One of SQLAlchemy's most powerful features.

Suppose

```python
merchant1 = repository.get_by_id(1)

merchant2 = repository.get_by_id(1)
```

Inside the same Session,

SQLAlchemy does NOT create two Python objects.

Instead

```
merchant1

↓

Same Object

↓

merchant2
```

Why?

Because they represent the same database row.

This feature is called

Identity Map.

It prevents inconsistent object state.

# 16. Common Misconceptions

❌ add() inserts data.

No.

It only registers the object with the Session.

---

❌ flush() commits data.

No.

Rollback can still undo everything.

---

❌ commit() sends SQL.

Not exactly.

Flush sends SQL.

Commit finalizes the transaction.

(Commit may trigger an automatic flush first if needed.)

---

❌ refresh() saves changes.

No.

It reloads data from the database.

---

❌ Session is the database connection.

No.

Session manages ORM objects and transactions.

It borrows database connections when necessary.

---

# 17. Summary Table

| Method | Purpose |
|---------|---------|
| add() | Register object with Session |
| flush() | Send SQL without committing |
| commit() | Permanently save transaction |
| refresh() | Reload object from database |
| rollback() | Undo current transaction |
| close() | Release database resources |

# Interview Questions

★★★★★ What is SQLAlchemy Session?

A Session is a unit of work that tracks ORM objects and manages database transactions.

---

★★★★★ Difference between flush() and commit()?

flush() sends SQL to the database but keeps the transaction open.

commit() permanently completes the transaction.

---

★★★★★ Why use refresh()?

To synchronize Python objects with database-generated values.

---

★★★★☆ Why use rollback()?

To undo partial work when a business operation fails.

---

★★★★☆ What is Identity Map?

A Session ensures one Python object represents one database row.

---

★★★★☆ Why doesn't add() execute SQL?

Because SQLAlchemy first tracks changes and sends SQL later during flush or commit.
